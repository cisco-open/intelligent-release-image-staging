Device-side troubleshooting

Start with the device's latest heartbeat, assigned images, and job log. An inventory row can exist before an agent connects. A successful onboard job confirms the installer finished; a fresh heartbeat confirms the agent can reach the catalog. Image staging happens afterward.

Read the device status

  • Waiting for staging: the assignment is saved, but the agent has not reported work on it yet. Allow for the normal 60-second tick, startup jitter, or a retry delay.
  • Staging: check the assigned image's progress and latest report. A fresh heartbeat proves contact, not a successful download.
  • Staging failed or Error: read the current image's error. An older staged result does not clear a new failure.
  • Staged: the agent verified and placed the image. A tracker peer at 100% only proves transfer completion; it does not confirm the IOS-XE copy to the storage root.
  • Stale or missing heartbeat: check the runtime and its path to the catalog below. Unassigned agents still heartbeat.

For multiple assignments, open the device details and check each image. The Swarm Map shows observations for a particular image and participant; an idle or unobserved peer is not evidence of a failed download.

Guest Shell and router agents

The IRIS-AGENT EEM applet runs bootstrap every 60 seconds. Check it from IOS-XE:

show event manager history events
show event manager statistics
show logging | include IRIS

The installer sets authorization bypass on the applet for devices using AAA command authorization. A missing applet, a failed bootstrap, or an IRIS ROOTCOPY-FAIL line identifies the next check.

Inside Guest Shell, the working directory is /flash/guest-share/iris on Catalyst 9300 or /bootflash/guest-share/iris on routers. Check iris-agent.conf, the public iris-catalog.pem, and any aria2c-launch-failed marker there. Keep configuration and secret-file contents out of shared logs.

Dropping a fresh bundle.tgz into the guest-share root upgrades the agent on the next tick. Console upgrades use Undeploy, then Onboard; preflight refuses an already-running agent.

IOx agents

show app-hosting list

The iris app must reach RUNNING. A new package can take several minutes to load. A failed onboard that left the app DEPLOYED or ACTIVATED can be retried from the Console; a running app requires undeploy before onboarding again.

IOx uses the common device container with IRIS_DEVICE_PLATFORM=iox. It needs the configured app IP, gateway, and VLAN, plus SSH access from the app to IOS for storage checks and final placement. Downloads use CAF persistent storage; Catalyst 9300 normally hands files to IOS through the SSD share, while IE-3400 uses SCP to the device. Check show logging | include IRIS for placement or SSH errors.

The package contains no server certificate. Onboarding copies the current public certificate into application data after activation and before starting the app. A missing runtime certificate, incorrect CAF_APP_APPDATA_DIR, or stale certificate stops the catalog and tracker clients.

IOS-XR agents

show appmgr application-table
show appmgr application name iris logs
dir harddisk:

The iris app must be Up. It uses the same device container as IOx, with IRIS_DEVICE_PLATFORM=xr-appmgr, host networking, and /misc/disk1:/hostmount. It uses the router's IP addresses and routes; there is no separate app IP, VLAN, or SSH-to-self connection.

Images download directly to harddisk:. The agent checks the bind mount before writing. Its configuration and state live in harddisk:iris-work/, and its runtime certificate is harddisk:iris-catalog.pem. Agent diagnostics appear in the appmgr log above. An empty iris-work/ directory after a successful undeploy is expected.

Network and certificate checks

All agents need HTTPS to the catalog on TCP 8443, HTTPS tracker announces on TCP 6969, and BitTorrent TCP 6881 to the server seeder. Device peers use TCP 6881–6999 in both directions; Router NAT publishes TCP 6881 through its outside address. Guest Shell onboarding also fetches artifacts over HTTPS on TCP 8000. The server opens SSH/SCP connections to devices on TCP 22; IOx also uses SSH/SCP from the app to IOS. These are the default ports.

Test from the agent's network context, using its public certificate. For example, from the Guest Shell working directory:

curl --connect-timeout 5 --max-time 15 --cacert iris-catalog.pem \
  -o /dev/null -w '%{http_code}\n' https://<server-ip>:8443/
curl --connect-timeout 5 --max-time 15 --cacert iris-catalog.pem \
  -o /dev/null -w '%{http_code}\n' https://<server-ip>:6969/

An HTTP response proves the route and certificate check, including a 401 or 404; it does not prove device authorization. A timeout needs a routing, ACL, VLAN, or NAT check. A refused connection needs a listener check. A TLS error needs the device clock, certificate, and server address checked. After server certificate rotation, undeploy and onboard affected agents to deliver the new certificate. IOx/XR packages do not need a rebuild for certificate rotation.

Aria2 JSON-RPC is local to the agent on 127.0.0.1:6800; do not publish it. Bootstrap and the common container supervisor check RPC health and restart a daemon that no longer serves requests. aria2c.log is disabled by default; enable IRIS_LOG only when you need that transfer log. Agent status and error messages remain available with it disabled.

Guest Shell commands: guestshell run does not perform shell quote processing. Open an interactive Guest Shell for the examples above, or stage a script file and run it.
