Device-side troubleshooting

The agent's first successful heartbeat is what makes a device appear in the console — nothing before that point is visible outside the device. Work this chain in order; each step assumes the previous one passed.

  1. Is the device heartbeating?
    Console → Devices: a green heartbeat means the agent is alive and talking to the catalog. Assignment only gates staging, not presence — an unassigned device still heartbeats. If the heartbeat is green, the problem is assignment or staging state, not the agent; stop here and check the device's report and assigned image instead.
  2. Is the EEM applet firing? (Guest Shell and router paths)
    The installer configures applet IRIS-AGENT on a 60-second watchdog timer. On the device: 
    show event manager history events
show event manager statistics
    No entries means the applet is missing or never runs — re-run the installer. On devices running AAA command authorization the applet must carry authorization bypass (the installer sets this); without it, IOS discards the applet's actions silently.
  3. What does syslog say?
    show logging | include IRIS
    Installer, bootstrap, and copy-to-root messages land here. An IRIS ROOTCOPY-FAIL entry carries the device-side detail behind a console placement failed status.
  4. Can the guest reach the server?
    The agent needs HTTPS to the catalog on :8443 and the artifact server on :8000. Probe from inside Guest Shell: 
    guestshell
curl -sk -o /dev/null -w '%{http_code}\n' https://<server-ip>:8443/
curl -sk -o /dev/null -w '%{http_code}\n' https://<server-ip>:8000/
    Any HTTP status code proves the path. Connection refused or a timeout is a routing/VLAN/NAT problem — check the device's management type and the server's published ports.
  5. Is aria2c serving?
    The download daemon answers JSON-RPC on loopback only. From inside the guest: 
    curl -s http://127.0.0.1:6800/jsonrpc \
  -d '{"jsonrpc":"2.0","id":"p","method":"aria2.getVersion","params":["token:'$(cat rpc-secret)'"]}'
    (run from the stage directory: /flash/guest-share/iris on Catalyst 9300, /bootflash/guest-share/iris on routers). A aria2c-launch-failed marker file in the stage directory means the daemon launch itself failed — see aria2c.log next to it for why. Supervision keys on RPC health: a healthy tick relaunches a non-serving daemon automatically.
  6. Is the agent bundle fresh?
    Dropping a new bundle.tgz into the stage directory is the upgrade for Guest Shell and router devices — the next 60-second tick unpacks and runs it. There is no separate upgrade command; re-running the installer has the same effect.
  7. IOx devices (Catalyst 9300 IOx, IE-3400)
    show app-hosting list
    The iris app must be RUNNING; if not, check the app-hosting logs on the device. TLS-rotation gotcha: IOx packages bake the catalog CA in at build time, so packages built before a server certificate rotation keep pinning the old cert — the app runs and TCP connects, but the device never heartbeats. Rebuild and restage with tools/provision-iox-packages.sh, then re-onboard the affected devices. Guest Shell devices heal on re-onboard automatically.
Warning: guestshell run performs no shell quote processing — quoted one-liners silently do nothing. Stage a script file on the device and run that instead.
