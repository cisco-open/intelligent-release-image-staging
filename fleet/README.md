# `fleet/` — inventory CSVs and generated installers

This directory holds the CSV templates for device inventory and image
assignments, and the per-device installers the legacy generator writes.

The operator manual is
[Fleet workflows](../docs/zensical/fleet-workflows.md); the CSV v2 schema is
documented in [Management type and VLAN
ownership](../docs/zensical/management-type.md#inventory-csv-v2). This file is
the directory-level orientation only — when the two disagree, the manual is
right.

## Files

| File | What it is |
| --- | --- |
| `devices.csv.example` | Template for the management-type-aware inventory (**CSV v2**). Every example row is commented out; copy it to `devices.csv` and edit. |
| `roles.csv.example` | Round-trippable role-definition template for `iris-role import` and `iris-role export`. List fields use semicolons. |
| `assignments.csv.example` | Template for `device_id,image_id` assignments, applied with `tools/apply-assignments.sh`. |
| `schedules.csv.example` | Round-trippable schedule template for `iris-schedule import` and `iris-schedule export`. The `target`, `payload`, `when` and `after` columns hold JSON, so the closed schedule schema survives a round trip unchanged. |
| `devices.csv`, `assignments.csv`, `roles.csv`, `schedules.csv` | Yours. Git-ignored. |
| `dist/` | Generated by `tools/gen-device-installers.sh`: `install-<device_id>.sh` per device plus `install-all.sh`. Git-ignored — each file embeds that device's enrollment token. |

`devices.csv` declares a `management_type` per row, one of **five**: `routed`,
`inband`, `router-routed`, `router-nat`, `xr-host`. The current header is the
one in `devices.csv.example`; the console validates against exactly that
column set, so copy it rather than retyping it.

The optional `role` column declares policy membership. Names use 1-32 lowercase
letters, numbers, dot, underscore, or hyphen. Inventory import is add/change
only for this field: a blank value preserves the stored role, including when an
older pre-role CSV is re-imported. Clear membership explicitly with
`iris-role set DEVICE_ID -` or the role API.

`iris-schedule import FILE` validates every row of a schedule CSV before it
writes anything, and `iris-schedule export` writes the same schema back. A
schedule is stage-only: its `kind` is `assign` or `onboard`, and neither
installs, activates, or reloads. Weekday numbering is Monday=0. See
[Scheduling](../docs/zensical/fleet-workflows.md#scheduling).

`iris-role export` writes the same scalar-only schema as `roles.csv.example` and
omits `qos_state`; restore it with `iris-role import FILE`. `iris-role define`
removes state from the role it replaces, and `iris-role import FILE` removes
state from every definition it replaces. The CLI validates the whole file,
duplicate rows, peer references, network prefixes, and QoS units before
writing. Use `--dry-run` on define, delete, set, bulk, and import changes.
Rates are bytes per second and intervals are seconds; role rows cannot carry the
global-only `origin_*` QoS settings. Configure, preserve, or remove state
through the management API. Preview reports `qos_changed`, and apply requires
the candidate-bound confirmation token. When you replace a full role
definition, include `qos_state` to retain its state.

## Getting devices onboarded

Onboarding a CSV v2 inventory runs through the **console**, not through
`tools/gen-device-installers.sh`. The console persists a deployment record,
resolves a plan, and runs preflight before any enrollment token is minted —
`gen-device-installers.sh` does none of that and refuses a header containing
`management_type` for exactly that reason.

1. Bring the server up with `tools/start-compose-server.sh`. (Do **not** run
   `docker compose up` directly on a fresh config volume: the entrypoint fails
   closed on the missing encrypted state and the container restart-loops.)
2. `cp devices.csv.example devices.csv`, fill in your devices, and import it on
   the console's Devices screen — or create the rows there directly.
3. Onboard from the console. See
   [Fleet workflows](../docs/zensical/fleet-workflows.md).

Assignments are the one CSV path that is still first-class from the command
line: `cp assignments.csv.example assignments.csv`, then
`tools/apply-assignments.sh --dry-run fleet/assignments.csv` to validate and
`tools/apply-assignments.sh fleet/assignments.csv` to apply.

## The legacy generator

`tools/gen-device-installers.sh` predates management types. It accepts only the
old positional, routed-only inventory
(`device_id,device_ip,vlan,svi_ip,svi_mask,guest_ip`) and refuses any CSV v2
header. No template for that format ships, because new deployments should use
the console; it exists for sites that still hold such a CSV.

It reads no configuration file. Its inputs are the command line and these
environment variables:

| Variable | Default | Effect |
| --- | --- | --- |
| `IRIS_HOST_IP` | this machine's first address | Derives `CATALOG_URL` and `STAGE_HOST`. |
| `IRIS_CONTAINER` | `iris` | Name of the running server container it reads `tls/crt.pem` from. |
| `IRIS_ENROLL_TTL` | `3600` seconds | Lifetime of the short-lived enrollment token baked into each installer. |
| `CATALOG_URL`, `STAGE_HOST` | derived from `IRIS_HOST_IP` | Override the derived values. |
| `OUT` | `fleet/dist` | Output directory. |

No permanent secret is ever baked into an installer: each carries a
short-lived enrollment token that the agent self-promotes to a full catalog
token on its first tick, and it fetches the aria2 RPC secret at that same
refresh.

After a package runs, the device self-deploys: its 60-second EEM timer unpacks
the dropped bundle, starts the BitTorrent client, and runs the agent — which
pulls the device's assigned image, verifies it, and stages it at the storage
root. **Staging only — never install, activate, or reload.**
